Prefill, Decode, KV Cache: 토큰 하나가 NPU 경로에서 생성되기까지

GET_ROWS부터 lm_head, argmax, 다음 token loop, <eos> 종료까지 데이터 흐름으로 보는 온디바이스 LLM 추론

이 문서의 핵심 메시지

추론은 크게 두 국면입니다. Prefill은 prompt 전체를 한 번에 처리해 KV cache를 채우는 단계이고, Decode는 직전에 생성된 token 하나를 입력으로 받아 KV cache를 읽고 다음 token을 반복 생성하는 단계입니다. 입력 쪽에서 GET_ROWS는 이미 정해진 token id를 embedding vector로 바꾸는 lookup이고, 출력 쪽에서 lm_head(output projection)는 최종 hidden으로 vocab 전체 logits를 만드는 큰 MUL_MAT입니다. 그 logits에 argmax/sampling을 적용해 고른 token id가 다음 decode step의 GET_ROWS 입력이 되고, 이 loop는 <eos> 같은 stop 조건이 나올 때까지 돕니다. Tie Word Embedding은 이 입력 weight와 출력 weight가 같은 tensor를 공유하는지 여부이며, NPU에서 실제 성능을 보려면 op가 graph에 있는지·scheduler가 HTP로 보냈는지·buffer가 HTP 호환인지·HMX/HVX path를 탔는지까지 로그로 확인해야 합니다.

이 문서는 자매 문서 gguf_q4_htp_pipeline.html(GGUF·Q4_0·HTP0-REPACK·Graph Build·Scheduler·HMX/HVX 설명)과 이어지며, 그쪽이 "weight가 어떻게 저장·배치되는가"를 다뤘다면 이 문서는 "추론 중 데이터가 실제로 어떻게 흐르는가"에 집중합니다. 모든 숫자는 개념 이해용 toy 값이며, 외부 리소스 없이 파일만 열면 동작합니다. 태그는 확정 가능성 구현 확인 필요로 구분합니다.

3.Prefill 상세 애니메이션

Prefill은 prompt token 여러 개가 한 번에 들어가는 대량 처리 단계입니다. 아래 예시는 이해를 위해 prompt token ids [17, 42, 391, 8]의 4-token toy example로 축소한 것입니다. 프로젝트 benchmark 기준은 input token length target 255, context length 2048이므로, 실제 embedding 결과 shape는 [255, hidden_size]에 가깝지만 여기서는 [4, 4]로 줄여 보여 줍니다. Prefill의 핵심 산출물은 다음 token 하나가 아니라, 모든 layer의 KV cache를 position 0~seq-1까지 채우는 것입니다.

4.Decode 상세 애니메이션

Decode는 token 하나씩 반복되는 loop입니다. 아래 예시는 현재 입력 token id 501, 현재 position 4이고, KV cache에는 이미 prefill이 채운 position 0~3이 들어 있는 상황입니다. Decode는 이번 token의 Q만 새로 계산하고, K/V는 새 것을 position 4에 append한 뒤 과거 cache(0~4)를 재사용해 attention을 계산합니다. 마지막에 lm_head로 logits를 만들고 argmax/sampling으로 다음 token을 고른 뒤, 그 token이 다시 GET_ROWS 입력으로 돌아갑니다. <eos>(예: id 2)가 선택되면 loop가 멈춥니다.

5.Tie Word Embedding on/off 애니메이션

Tie Word Embedding은 입력 embedding과 출력 lm_head가 같은 weight tensor를 공유하는지 여부입니다. 아래 토글로 on/off를 바꿔 보세요. off일 때는 입력이 token_embd.weight, 출력이 별도의 lm_head.weight(또는 output.weight)를 씁니다. on일 때는 입력 GET_ROWS와 출력 MUL_MAT가 같은 token_embd.weight를 공유합니다 — 다만 입력에서는 "row 하나 꺼내기(lookup)"로, 출력에서는 "vocab 전체 projection 행렬"로 access pattern이 다르게 쓰입니다.

자주 하는 오해 — Tie Word Embedding은 "argmax 이후에 GET_ROWS를 한다"는 뜻이 아닙니다. 입력 쪽 GET_ROWS와 출력 쪽 lm_head MUL_MAT가 같은 weight를 공유할 수 있다는 뜻입니다. (물론 argmax로 고른 token은 다음 step에서 다시 GET_ROWS 입력이 되지만, 그건 tie와 별개의 loop 이야기입니다.)
—
NPU 관점 가능성 구현 확인 필요 — 같은 weight라도 입력은 row lookup에 좋은 layout을, 출력 MUL_MAT은 tile-major(HTP0-REPACK) layout을 선호합니다. 두 access pattern을 하나의 저장 layout으로 동시에 만족시키기 어려울 수 있어, backend가 내부적으로 같은 값의 weight를 서로 다른 layout으로 중복 보관할 가능성이 있습니다. 이것이 실제로 그런지는 backend 구현과 메모리 사용량 로그로 확인해야 합니다.

6.GET_ROWS vs lm_head MUL_MAT 비교

입력 쪽 GET_ROWS와 출력 쪽 lm_head는 같은 vocab weight를 만질 수 있지만 하는 일이 정반대입니다. GET_ROWS는 vocab table에서 row 하나만 꺼내 embedding을 만들고, lm_head는 최종 hidden을 모든 vocab row와 내적해 점수표(logits)를 만듭니다.

7.KV Cache 상세 애니메이션

KV cache는 과거 token들의 K(key)와 V(value)를 저장해 두는 메모리입니다. 캐시가 없으면 decode 매 step마다 prompt 전체를 처음부터 다시 계산해야 하지만, 캐시가 있으면 현재 token의 Q만 새로 만들고 K/V는 새 것을 append하면서 과거 cache를 재사용합니다. 아래 애니메이션은 layer별 cache bank를 그리고, prefill이 position 0~3을 한 번에 채운 뒤 decode가 position 4·5를 하나씩 append하며 현재 Q가 과거 K/V 전체를 읽는 흐름을 보여 줍니다.

KV cache 배치는 성능 급소 구현 확인 필요 — KV cache의 위치(HTP 가까운 memory인지 DDR인지)와 dtype, 그리고 CPU↔HTP 왕복 여부가 decode 성능에 큰 영향을 줍니다. cache가 HTP에서 멀리 있으면 매 step read/write마다 복사가 생길 수 있습니다. 이는 실제 backend 구현과 로그로 확인해야 합니다.

8.NPU/HTP Backend Path Overlay

아래는 각 op가 어느 backend에서 돌 수 있는지를 배지로 겹쳐 본 것입니다. good path에서는 주요 matmul이 HTP로 가고 Q4_0 weight가 HTP0-REPACK에 있으며 HMX/HVX tiled 후보 경로를 탑니다. fallback path에서는 GET_ROWS나 일부 elementwise op가 CPU에 남아 matmul 전후로 activation 복사가 생기고 HTP split이 끊깁니다. 토글로 두 시나리오를 비교해 보세요.

모든 배지는 예시 시나리오입니다 구현 확인 필요. 실제 결과는 graph dump, schedule dump, HTP profile로 확인해야 하며, "op 이름이 MUL_MAT"이라는 사실만으로 HMX/HVX를 탔다고 단정할 수 없습니다.

9.Prefill vs Decode 비교 애니메이션

같은 model forward라도 prefill과 decode는 shape·병목·NPU 할당 조건이 다릅니다. Prefill은 여러 token [seq, hidden]이 한꺼번에 흐르며 KV cache를 대량으로 write하고 큰 matmul로 병렬성이 높아 first token latency에 영향을 줍니다. Decode는 token 하나 [1, hidden]이 loop를 돌며 KV cache를 append+전체 read하고 weight를 반복해서 읽어 memory-bound 성향이 강해 tok/s·ms/token에 영향을 줍니다.

10.실제 graph와 애니메이션의 차이

이 문서의 모든 애니메이션은 이해를 돕기 위한 축약판입니다. 실제 llama.cpp/ggml graph에서는 한 칸이 GET_ROWS, RMS_NORM, MUL_MAT, ROPE, ADD, MUL, SILU, CONT, VIEW, CPY 등 더 세분화된 node로 나타날 수 있고, shape도 toy vector가 아니라 훨씬 큰 실제 차원을 가집니다. 각 node가 실제로 어느 backend에 배치됐는지는 graph dump와 schedule dump를 봐야 하고, HMX/HVX 여부는 op 이름이 아니라 HTP backend 내부 path 선택 로그 또는 PMU/profile로 판단해야 합니다. 이 문서의 backend 배지는 모두 "예시 시나리오"라는 점을 다시 강조합니다.

자매 문서 gguf_q4_htp_pipeline.html의 graph dump 절에 graph_nodes.txt/graph_schedule.txt로 node와 backend 배치를 확인하는 방법이 정리되어 있습니다. 이 문서의 데이터 흐름과 그쪽의 graph/scheduler 관점을 함께 보면 "무엇이 흐르는가"와 "그것이 어디서 실행되는가"를 연결해서 이해할 수 있습니다.
