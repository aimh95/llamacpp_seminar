Qualcomm HTP 적용 관점 · ixi_gen 1.2B Semantic Agent PoC

이 문서가 답하는 질문 — "모델의 나머지 weight는 Q4_0으로 두고, token_embd.weight(토큰 임베딩) 하나만 Q8_0으로 더 정밀하게 만들려면 어떻게 하는가? 그리고 그것이 Qualcomm HTP(Hexagon NPU) 위에서 실제로 의미가 있으려면 무엇을 확인해야 하는가?" 이 문서는 그 방법(llama-quantize 명령)과 원리(블록 양자화·GET_ROWS·tied embedding), 그리고 HTP 검증 절차를 초급 개발자 눈높이로 정리합니다.
먼저 못 박아 둘 것 — GGUF의 Q8_0은 weight를 8bit 블록으로 저장하는 것이지, activation까지 int8로 만드는 W8A8(qint8) 양자화가 아닙니다. 이 구분은 문서 전체에서 반복해서 강조합니다. 또한 여기 나오는 HTP 지원 관련 서술은 대부분 "확인 필요"이며, 실제 지원 여부는 현재 checkout한 llama-quantize --help·llama-quant.cpp·test-backend-ops 결과로 검증해야 합니다.

1.핵심 명령: token embedding만 Q8_0으로

목표는 "기본은 Q4_0, 예외적으로 token embedding만 Q8_0"인 mixed precision GGUF를 만드는 것입니다. 아래 명령이 그 조합입니다.

cd /home/iptv-infra/workspace/llamacpp-aos-benchmark

mkdir -p artifacts/quant

build-host/bin/llama-quantize \
  --pure \
  --token-embedding-type q8_0 \
  models/ixi_gen_1p2b_f16.gguf \
  models/ixi_gen_1p2b_q4_0_tokemb_q8_0.gguf \
  Q4_0 \
  2>&1 | tee artifacts/quant/ixi_gen_q4_0_tokemb_q8_0.log

옵션을 한 줄씩

  • Q4_0 — 명령 끝의 위치 인자로, 모델의 기본 양자화 형식입니다. 양자화 가능한 대부분의 2D/3D weight(attention·FFN의 matmul weight 등)를 Q4_0으로 변환합니다.
  • --token-embedding-type q8_0 — token embedding tensor만 Q8_0으로 override합니다. 일반적으로 대상 tensor 이름은 token_embd.weight입니다. 즉 기본 Q4_0 규칙에서 이 tensor 하나만 예외로 빼냅니다.
  • --pure — 기본 recipe가 일부 tensor를 Q5_K/Q6_K 등으로 자동 승격하는 것을 방지합니다. 실험 변수를 줄여 "token embedding만 Q8_0, 나머지는 순수 Q4_0"이라는 조건을 명확하게 만들어 줍니다.
  • models/ixi_gen_1p2b_f16.gguf — 입력(재양자화 원본). FP16 GGUF가 원본으로 적합합니다.
  • models/ixi_gen_1p2b_q4_0_tokemb_q8_0.gguf — 출력 파일 경로(이름에 조건을 담아 두면 나중에 헷갈리지 않습니다).
  • 2>&1 | tee ...log — 표준에러까지 합쳐 로그 파일로 저장합니다. 나중에 어떤 tensor가 어떤 타입으로 갔는지 grep으로 확인하는 근거가 됩니다.

개념 구조: 기본값 · 예외 · 유지

blk.*.attn_q/k/vattn_outputffn_gate/up/down

2.내부 처리 흐름

llama-quantize가 위 명령을 받으면 tensor를 하나씩 순회하며 "이 tensor를 어떤 타입으로 저장할지"를 결정합니다. 흐름은 대략 다음과 같습니다.

▼
② tensor 이름 · architecture 분류

▼
③ TOKEN_EMBD 여부 확인
이 tensor가 token embedding인가?
▼
④ token_embd.weight → Q8_0 선택

▼
⑤ 나머지 양자화 대상 → Q4_0 선택

▼

▼

tensor별로 서로 다른 타입이 섞인 파일 기록

개념 의사 코드

# 개념 설명용 pseudo-code (실제 llama-quantize 내부 구조와 1:1은 아님)
for tensor in gguf_tensors:
    if not is_quantizable(tensor):        # norm, bias, 작은 1D tensor 등
        target_type = keep_original       # F16 / F32 유지
    elif tensor.category == TOKEN_EMBD:
        target_type = Q8_0                 # --token-embedding-type q8_0
    else:
        target_type = Q4_0                 # 기본 타입 (--pure로 승격 억제)

    write_tensor(quantize(tensor, target_type))
주의 — 위에서 보듯 norm/bias 등은 애초에 is_quantizable이 아니어서 양자화에서 제외될 수 있습니다. 즉 "예외 = Q8_0" 규칙보다 앞서 "양자화 제외" 규칙이 먼저 걸립니다.

3.Q4_0과 Q8_0 block 구조

block 양자화 = weight를 32개씩 한 묶음(block)으로 나누고, 그 32개를 대표하는 scale 값 하나와 각 weight의 정수 코드로 저장하는 방식. 복원 시 weight ≈ scale × code로 되돌립니다.

Q4_0 — weight당 4bit

scale
FP16
2 bytes
32 weight × 4bit = 16 bytes

total = 2 + 16 = 18 bytes / 32 weight → effective ≈ 4.5 bits per weight (bpw)

Q8_0 — weight당 8bit

scale
FP16
2 bytes
32 weight × int8 = 32 bytes

total = 2 + 32 = 34 bytes / 32 weight → effective ≈ 8.5 bits per weight (bpw)

bpw (bits per weight) = weight 하나당 실제로 쓰는 평균 비트 수. scale 같은 부가정보까지 포함해서 나눈 값이라, "4bit 양자화"인데 bpw가 4.5인 이유가 여기에 있습니다.
타입block weight 수값 저장 크기scale총 크기실효 bpw
Q4_03216 bytes2 bytes18 bytes4.5
Q8_03232 bytes2 bytes34 bytes8.5

token embedding을 Q4_0 → Q8_0으로 바꿀 때 늘어나는 크기

차이는 weight당 8.5 − 4.5 = 4 bit = 0.5 byte입니다. 따라서 대략:

추가 크기 ≈ vocab_size × embedding_dim × 0.5 bytes

예시:
  vocab_size    = 32,000
  embedding_dim = 2,048
  추가 크기 ≈ 32,000 × 2,048 × 0.5 = 32,768,000 bytes ≈ 약 31~32 MiB
이 값은 예시입니다 — 실제 추가 크기는 모델의 vocab_size·embedding_dim, 그리고 tensor 구성/metadata에 따라 달라집니다. bpw와 파일 크기 모두 정확한 수치는 실제 GGUF로 확인해야 합니다.

4.token embedding과 GET_ROWS

GET_ROWS = 큰 embedding 행렬(token_embd.weight)에서 특정 token ID에 해당하는 row(행) 하나만 꺼내오는 lookup 연산. 전체 행렬 곱(matmul)이 아니라 "표에서 한 줄 찾기"에 가깝습니다.

  • embedding은 일반적인 전체 matrix multiplication이 아니라, token ID에 해당하는 row를 읽어오는 연산입니다.
  • Q8_0으로 저장하면 Q4_0보다 embedding 값의 세밀한 차이를 더 보존할 수 있습니다(8bit vs 4bit).
  • 단, 품질 개선 폭은 모델마다 다르며 반드시 평가가 필요합니다. "정밀도를 올렸으니 무조건 좋아진다"고 단정할 수 없습니다.

5.tied embedding일 때의 영향

tied embedding (weight tying) = 입력 임베딩 행렬(token_embd.weight)과 출력 logits를 만드는 행렬(output.weight/lm_head)이 같은 tensor를 공유하는 구조. 메모리를 아낄 수 있지만, 그 하나의 tensor가 입력과 출력 양쪽에 동시에 쓰입니다.

Untied (분리)

token_embd.weight
▼ 입력 embedding 전용
GET_ROWS
output.weight
▼ 최종 logits 전용
lm_head / output projection (MUL_MAT)

Tied (공유)

token_embd.weight
▼ 입력
GET_ROWS (embedding lookup)
▼ 같은 weight 재사용
lm_head / output projection (MUL_MAT)
중요 경고 — tied embedding 모델에서 token_embd.weight를 Q8_0으로 바꾸면, 입력 embedding뿐 아니라 최종 logits 계산의 정밀도와 backend 지원 여부에도 영향을 줍니다. 이 경우 embedding lookup(GET_ROWS)의 Q8_0 지원만이 아니라, 출력 projection(MUL_MAT)의 Q8_0 지원까지 함께 필요합니다. 또한 GGUF에 output.weight가 별도로 존재하지 않는다면 tied embedding일 가능성이 큽니다 — 반드시 확인해야 합니다.

tied 여부는 다음처럼 GGUF에서 두 tensor 존재를 확인해 추정할 수 있습니다.

python third_party/llama.cpp/gguf-py/gguf/scripts/gguf_dump.py \
  models/ixi_gen_1p2b_f16.gguf \
  | grep -E 'token_embd\.weight|output\.weight'

token_embd.weight만 보이고 output.weight가 없으면 tied embedding일 가능성이 높습니다(모델·변환 방식에 따라 다르므로 최종 확인은 architecture/config로).

6.양자화 결과 검증

양자화가 끝나면 "정말 token_embd만 Q8_0이고 나머지는 Q4_0인지"를 로그와 GGUF dump로 확인합니다.

① 로그에서 확인

grep -Ei \
'token_embd|token embedding|output\.weight|quantizing to|q8_0|q4_0' \
artifacts/quant/ixi_gen_q4_0_tokemb_q8_0.log

② GGUF dump에서 tensor 타입 확인

python third_party/llama.cpp/gguf-py/gguf/scripts/gguf_dump.py \
  models/ixi_gen_1p2b_q4_0_tokemb_q8_0.gguf \
  > /tmp/ixi_gen_mixed_dump.txt

grep -E \
'token_embd\.weight|output\.weight|blk\.0\.(attn|ffn)' \
/tmp/ixi_gen_mixed_dump.txt | head -50
성공 기준
  • token_embd.weight → Q8_0
  • 주요 blk.* weight(attn/ffn) → Q4_0
  • norm/bias 등 → F16/F32일 수 있음
  • output.weight는 tied 여부에 따라 존재하지 않을 수 있음

7.2 Legacy Q 계열

Q4_0

거의 symmetric한 block quantization. 32개 weight당 scale 하나. 구조가 단순해 backend kernel 구현이 쉽고, Qualcomm HTP PoC의 우선 검증 대상입니다.

Q4_1

scale과 min/offset을 함께 저장해 비대칭 분포 표현에 유리합니다. 대신 Q4_0보다 파일이 큽니다.

Q5_0

Q4_0과 유사하되 weight당 5bit. 품질·크기가 Q4_0과 Q8_0의 중간입니다.

Q5_1

Q4_1 구조의 5bit 버전. scale + min을 사용합니다.

Q8_0

8bit weight + block scale. 품질 손실이 비교적 작아 mixed precision에서 민감 tensor(예: token embedding)에 부분 적용하기 좋습니다.

타입실효 bpw상대 크기품질HTP PoC 권장도
Q4_0약 4.5작음중간높음
Q4_1약 5.0중간Q4_0보다 높음지원 확인 필요
Q5_0약 5.5중간 이상높음지원 확인 필요
Q5_1약 6.0큼높음지원 확인 필요
Q8_0약 8.5큼매우 높음부분 적용 후보

7.3 K-quant 계열

K-quant = 여러 weight를 큰 super-block으로 묶고, 그 내부를 다시 작은 sub-block으로 나눠 sub-block마다 scale/min을 정밀하게 적용하는 GGUF 양자화 방식. 같은 평균 bit 수라도 단순 Q4_0보다 값 분포를 더 정밀하게 표현합니다.
반드시 구분 — Q4_K는 실제 tensor storage type(한 tensor가 저장되는 형식)이고, Q4_K_M은 모델 전체 quantization recipe(어떤 tensor를 어떤 타입으로 섞을지의 조합)입니다. 여기서 K는 K-quant/super-block 구조를, M은 Medium mixed recipe를 뜻합니다.
super-block ≈ 256 weight (super-scale 공유) — 내부를 sub-block으로 다시 분할
scale/minsub-block
scale/minsub-block
scale/minsub-block
scale/minsub-block
…16 또는 32 단위

보통 256개 weight를 하나의 super-block으로 묶고, 내부를 16개 또는 32개 단위 sub-block으로 다시 나눠 sub-block별 scale/min을 사용합니다. tensor storage type과 대략적인 effective bpw는 다음과 같습니다.

타입대략 effective bpw
Q2_K약 2.625
Q3_K약 3.4375
Q4_K약 4.5
Q5_K약 5.5
Q6_K약 6.5625

모델 recipe와 S / M / L 접미사

다음은 tensor 타입이 아니라 모델 전체 recipe입니다: Q2_K_S, Q2_K, Q3_K_S, Q3_K_M, Q3_K_L, Q4_K_S, Q4_K_M, Q5_K_S, Q5_K_M, Q6_K.

S / M / L = Small / Medium / Large. 하나의 tensor block 인코딩 차이가 아니라, 모델 전체에서 민감 tensor를 어떤 고정밀 타입으로 승격할지 결정하는 recipe 단계입니다.
단계고정밀 승격 tensor파일 크기품질 손실
S (Small)가장 적음가장 작음가장 큼
M (Medium)중간중간중간(균형)
L (Large)가장 많음가장 큼가장 적음

예시:

  • Q4_K_M — 대부분 weight → Q4_K, 일부 민감 tensor → Q5_K 또는 Q6_K, norm 등 → F16/F32.
  • Q5_K_M — 대부분 weight → Q5_K, 일부 민감 tensor → Q6_K.
버전 의존 — Q4_K_M 등이 실제로 어떤 tensor를 어떤 타입으로 승격하는지는 모델 architecture와 llama.cpp 버전에 따라 달라집니다. 정확한 매핑은 현재 checkout한 llama-quant.cpp와 dump 결과로 확인하세요.

7.4 IQ 계열 (초저비트)

IQ (importance-aware / non-linear quant) = 단순 선형 int 양자화 대신 codebook과 importance matrix(imatrix) 정보를 적극 활용해, 아주 낮은 bit에서도 품질을 최대한 지키려는 형식.

타입: IQ1_S, IQ1_M, IQ2_XXS, IQ2_XS, IQ2_S, IQ2_M, IQ3_XXS, IQ3_XS, IQ3_S, IQ3_M, IQ4_XS, IQ4_NL.

  • 저비트에서 품질을 최대한 유지하기 위한 형식이며, imatrix가 중요할 수 있습니다.
  • backend kernel 지원 범위가 제한될 수 있습니다(특히 NPU 계열).
XXS / XS / S / M = extremely-extra-small / extra-small / small / medium. 같은 bit 계열 안에서 더 공격적으로 줄일수록 XXS 쪽입니다.

낮은 bit일수록 일반적으로: 파일 크기 감소 · RAM 감소 ↔ 품질 저하 위험 증가 · kernel 지원 제한 증가 · dequantization 비용 증가 가능.

7.5 특수 / 실험 양자화

다음은 특수·실험 성격입니다: TQ1_0, TQ2_0(ternary 계열), MXFP4_MOE, NVFP4(FP4 계열/특정 하드웨어), Q1_0, Q2_0.

경고 — 이들은 모든 backend와 모델에서 지원되지 않으며, 실험용이거나 특정 하드웨어/모델용입니다. PoC 초기에 손대는 것은 권장하지 않습니다.

8.Qualcomm HTP 적용 관점

프로젝트 핵심 조건
  • 타깃: Android ARM64, Qualcomm Snapdragon Gen4 계열
  • NPU: HTP V75 후보 파일명/단말 정보 기반 후보
  • backend: llama.cpp Snapdragon Hexagon backend
  • 모델: ixi_gen 1.2B · 기준 quant: Q4_0 · 목표: Semantic Agent PoC

핵심은 "GGUF가 지원하는 타입"과 "Hexagon backend가 실제로 kernel을 가진 타입"은 다르다는 점입니다.

  1. llama.cpp가 GGUF 타입을 지원해도, Hexagon backend가 해당 타입의 kernel을 지원한다고 보장할 수 없습니다.
  2. mixed precision tensor 중 하나라도 HTP에서 지원되지 않으면 그 op는 CPU fallback될 수 있습니다.
  3. 그 결과 HTP↔CPU tensor 이동(copy)이 발생하면 latency가 악화될 수 있습니다.
  4. 따라서 PoC에서는 "품질이 높은 quant"보다 "HTP native 지원 quant"가 더 중요할 수 있습니다.
  5. 현재 우선 후보: ① Q4_0 전체, ② Q4_0 + token_embd.weight Q8_0.
  6. 후순위: Q4_K_M, IQ 계열, 초저비트 quant.
  7. K-quant는 HTP kernel/repack 지원을 먼저 확인해야 합니다 — 일반 backend에서 잘 돌아도 HTP에서 지원한다는 뜻은 아닙니다.
다시 강조 — Q8_0은 weight를 8bit로 저장하는 GGUF block quantization이며, activation까지 int8로 만드는 W8A8(qint8)이 아닙니다. HTP에서 "Q8_0 지원"이란 곧 Q8_0 weight를 다루는 kernel(GET_ROWS / MUL_MAT)이 있는지를 뜻합니다.

  • 지원하지 않으면 embedding lookup이 CPU fallback될 수 있습니다.

HB=0 S=R3CX403LWAB \

Decode 경향 — 모든 quant에서 CPU가 빠르고, weight가 작아질수록 CPU 우위가 커집니다: F16 1.84× → Q8_0 1.92× → Q4_0 2.49× → Q4_K_pure 2.70×. Decode는 batch-1 memory-bound라 CPU가 작은 weight에서 이득을 더 보는 반면, HTP는 token당 dispatch·backend 전환 고정 overhead가 남아 못 따라가는 것으로 추정됩니다(op별 실행 backend 계측 필요 확인 필요).

핵심 해석

확인된 것
  • HTP 메모리 배치 — F16(2296.50) · Q8_0(1084.26) · Q4_0(574.25) MiB에는 HTP에 대형 weight가 올라간다. 반면 Q4_K 계열은 0.50 MiB — htp_layers=31만 보고 실제 offload를 판단하면 안 된다.
  • Prefill — F16/Q8_0/Q4_0에서 HTP 가속이 크다(Q4_0 HTP 151.44 vs CPU 528.58, ≈3.49×). Q4_K는 HTP 가속이 거의 없거나 일관되지 않다.
  • Decode — 모든 quant에서 현재 CPU-only가 더 빠르다(Q4_0 HTP 56.30 vs CPU 22.62 ms/tok, CPU ≈2.49×). "NPU 연결 성공"과 "Decode 가속"은 별개다.
token_embd Q8_0 관점(이 문서 주제와의 연결) — 이 mixed 구성이 HTP에서 완전한 이득을 보려면, 이 문서 9장의 GET_ROWS Q8_0과 (tied라면) MUL_MAT Q8_0가 실제로 HTP에서 지원돼야 합니다. 위 결과의 Decode CPU 우위는 embedding/LM Head가 CPU에 남아 token당 CPU↔HTP 왕복이 생기는 정황과 연결되지만, 이는 아직 가설이며 op별 실행 backend 계측이 필요합니다.
데이터 주의 (TPS ↔ ms/token 불일치) — CSV의 decode_tps는 1000 / decode_ms_per_tok과 정확히 일치하지 않는다(예: Q4_0 HTP 56.30 ms → 역산 ≈17.76 이지만 CSV는 20.07). 측정 구간·warm-up·첫 token 포함 여부·파싱 차이가 원인일 수 있으므로, 상대 비교는 ms/token을 우선 기준으로 삼는다.

※ 차트·필터·정렬이 포함된 발표용 상세 분석은 별도 세미나 문서에 있습니다: llamacpp-aos-benchmark/artifacts/seminar/exaone_htp_quant_seminar.html. 메모리 repack 로그(Q4_0 HTP0-REPACK 573.75 MiB ≈ CPU-only 678.75의 84.5%)와 supports-op GET_ROWS ... no 근거도 그 문서에 정리돼 있다.

12.실무 결론

  • token_embd.weight만 Q8_0으로 만드는 것은 GGUF mixed precision으로 가능합니다.
  • --pure --token-embedding-type q8_0 ... Q4_0 조합이 실험 변수를 가장 명확하게 통제합니다.
  • Q8_0은 qint8 W8A8과 같은 의미가 아니라 GGUF weight block quantization입니다.
  • tied embedding이면 출력 projection에도 영향을 줍니다.
  • Qualcomm HTP에서는 GET_ROWS Q8_0과 MUL_MAT Q8_0 지원을 별도로 검증해야 합니다.
  • Q4_K_M 등 K-quant는 일반 backend에서는 유용하지만 HTP 지원 여부를 먼저 확인해야 합니다.
  • PoC 우선순위: Q4_0 HTP 성공 → token embedding Q8_0 → 성능·품질 비교 순서.

＊확인이 필요한 기술적 가정

  • HTP가 특정 GGUF 타입(예: Q8_0의 GET_ROWS/MUL_MAT, K-quant)을 지원하는지는 단정하지 않았습니다 — test-backend-ops로 실측이 필요합니다.
  • HTP V75는 파일명·단말 정보 기반 후보 표현입니다. 실제 칩/버전은 단말에서 확인해야 합니다.
  • Q4_K_M의 tensor recipe는 모델 architecture와 llama.cpp 버전에 따라 달라질 수 있습니다.
  • 정확한 지원 타입 목록은 현재 checkout한 llama-quantize --help, llama-quant.cpp, test-backend-ops 결과를 기준으로 확인해야 합니다.
  • bits-per-weight와 파일 크기는 tensor 구성 및 metadata에 따라 달라질 수 있습니다.
  • Q8_0은 activation까지 int8로 만드는 W8A8 양자화가 아닙니다(weight-only block quant).
  • ixi_gen 1.2B의 tied embedding 여부, vocab_size, embedding_dim은 실제 config/GGUF로 확인해야 합니다(문서의 32000·2048은 예시).
