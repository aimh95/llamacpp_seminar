GGUF Q4_0에서 HTP/HVX/HMX 실행까지: Weight가 NPU Kernel로 내려가는 전체 흐름

Gemma-4 e2b 모델을 Qualcomm Gen4 NPU(Hexagon HTP) 위에서 추론 가능하게 만드는 PoC를 위한 기술 해설 문서 · 온디바이스 LLM 최적화

1.전체 한 장 요약

온디바이스 LLM을 NPU에서 돌리는 작업은 "모델 파일 하나를 통째로 칩에 밀어 넣는" 일처럼 들리지만, 실제로는 훨씬 잘게 쪼개진 과정의 연속입니다. 먼저 Hugging Face에 공개된 FP16 또는 BF16 형식의 원본 가중치를 GGUF라는 컨테이너 포맷으로 변환하고, 이 과정에서 가중치를 Q4_0이라는 4비트 양자화 형식으로 압축해 GGUF 파일 안의 metadata·tensor info·tensor data 영역에 나누어 저장합니다. 이 파일을 llama.cpp 런타임이 구동될 때 llama_model_loader가 열어서 각 텐서의 이름·shape·타입을 파싱하고, load_tensors 단계에서 각 텐서를 어떤 backend buffer에 배치할지 — CPU 메모리에 그대로 매핑(CPU_Mapped)할지, HTP(Hexagon Tensor Processor) 전용 버퍼로 보낼지, 그리고 HTP로 보낸다면 kernel이 읽기 좋은 순서로 재배치한 HTP0-REPACK 버퍼로 만들지를 결정합니다. 이후 추론 시점에는 build_attn, build_ffn 같은 함수들이 실제 계산을 곧바로 실행하는 대신 연산 그래프의 노드를 만들고(graph build), scheduler가 각 노드에 대해 supports_op·supports_buft를 검사해 이 연산을 CPU에서 돌릴지 HTP에서 돌릴지를 결정합니다. HTP로 배정된 노드는 HTP graph_compute라는 host-side 준비 코드를 거쳐 GGML 연산자를 HTP 고유의 opcode로 매핑하고, 필요하면 여러 연산을 fusion하고, matmul 파라미터를 계산한 뒤 dspqueue를 통해 실제 DSP(HTP) 코어로 작업을 넘기며, 그 코어 안에서 HMX(행렬곱 특화 유닛)나 HVX(벡터 유닛) kernel이 실제 곱셈-누산을 수행합니다.

핵심 메시지 — 이 전체 흐름에서 가장 중요한 사실은, "모델을 NPU에 올린다"는 표현이 실제로는 텐서 하나하나의 배치(tensor placement)와 연산 그래프 노드 하나하나의 스케줄링(graph node scheduling)이 조합된 결과라는 점입니다. 어떤 텐서는 CPU 메모리에 남고, 어떤 텐서는 HTP 전용 레이아웃으로 재포장되며, 어떤 연산은 HTP에서 돌고 어떤 연산은 여전히 CPU로 fallback됩니다. "GGUF가 Q4_0이다"라는 사실 하나만으로는 "HTP에서 빠르게 돈다"는 결론이 자동으로 따라오지 않습니다 — 그 사이에는 buffer placement, layout 재배치, scheduler 판정이라는 여러 단계가 더 있습니다.

2.전체 파이프라인 그림

아래 그림은 원본 FP16 모델부터 실제 HTP/HVX/HMX kernel 실행까지 데이터와 제어가 흘러가는 14개의 단계를 순서대로 보여줍니다. 각 박스 아래의 작은 글씨는 그 단계가 실제로 하는 일을 한 줄로 요약한 것입니다.

3.GGUF 파일은 무엇을 담는가

GGUF는 단순히 "가중치 숫자들이 쭉 나열된 배열"이 아닙니다. GGUF는 컨테이너 포맷이며, 하나의 파일 안에 서로 다른 역할을 가진 네 가지 구획이 순서대로 들어 있습니다: header(매직 넘버·버전·텐서 개수 등), metadata(모델에 대한 key-value 정보), tensor info(각 텐서의 이름·shape·타입·offset), 그리고 tensor data(실제 weight bytes가 들어 있는 큰 바이너리 블록)입니다.

metadata에는 예를 들어 이런 키들이 들어갑니다.

  • general.architecture — 이 모델이 어떤 아키텍처(예: gemma, llama)인지
  • general.name — 모델 이름
  • <arch>.embedding_length — hidden state / embedding 차원 수
  • general.file_type — 전체 파일이 어떤 양자화 타입 조합을 쓰는지에 대한 힌트
  • tokenizer.ggml.tokens — 토크나이저 vocab 목록

tensor info 구획에는 token_embd.weight, blk.0.attn_q.weight 같은 이름과 함께 각 텐서의 shape, 데이터 타입(F32, F16, Q4_0 등), 그리고 tensor data 블록 내에서의 byte offset이 기록됩니다. 실제 weight 숫자들은 이 offset을 따라 tensor data 영역에 순서대로 이어 붙어 있습니다.

혼동하기 쉬운 지점 — "GGUF는 nibble-packed 포맷이다"라는 말은 정확하지 않습니다. GGUF 파일 전체가 nibble-packed인 것이 아니라, Q4_0 타입으로 지정된 개별 텐서의 tensor data 영역만 nibble-packed block_q4_0 형식입니다. 같은 GGUF 파일 안에서도 어떤 텐서는 F32로, 어떤 텐서는 F16으로, 어떤 텐서는 Q4_0으로 저장될 수 있고, 이는 general.file_type 메타데이터와 각 텐서의 개별 타입 필드에 의해 결정됩니다.

4.Q4_0 양자화: FP16 32개가 Q4_0 block 하나가 되는 과정

Q4_0의 기본 단위는 block입니다. FP16 weight 32개를 하나의 block으로 묶어서, 그 32개 값을 대표할 수 있는 scale 값 1개와 각 weight를 4비트로 근사한 code 32개로 바꿉니다. 여기서 반드시 짚고 넘어가야 할 오해가 있습니다.

block 하나 = weight 32개 + scale 1개이지, weight 33개가 아닙니다. scale은 "33번째 weight"가 아니라, 나머지 32개의 4bit code를 원래 크기의 값으로 복원하기 위한 기준값(곱셈 계수)입니다. code 하나만으로는 "대략 몇 배 크기인지"를 알 수 없기 때문에, block 전체가 공유하는 scale과 곱해야 비로소 근사된 원래 weight 값이 나옵니다.

양자화(복원) 관계식은 대략 다음과 같습니다.

// 개념 설명용 pseudo-code — 실제 llama.cpp 구현의 세부 인덱싱과는 다를 수 있음
struct block_q4_0 {
    fp16  scale;      // 이 block 32개 weight를 대표하는 배율값 (2 bytes)
    uint8 qs[16];      // 4bit code 32개 = 16 bytes (한 byte에 code 2개)
};

// 복원(dequantize) 개념
weight[i] ≈ scale * (code[i] - 8)   // code는 0~15 범위의 4bit 값

byte 크기로 계산해 보면 압축 효과가 분명해집니다. FP16 weight 32개는 32 × 2 bytes = 64 bytes입니다. 같은 32개를 Q4_0 block 하나로 바꾸면 scale 2 bytes + qs 16 bytes = 18 bytes가 됩니다. 정확히 4배는 아니고(scale 오버헤드 때문에) 약 3.56배 압축입니다.

항목FP16Q4_0
weight 32개64 bytesscale 2B + qs 16B = 18 bytes
압축 비율1×약 3.56×

embedding 차원에 적용해 보기

embedding 차원이 d_embedding = 1024인 모델을 예로 들면, 한 토큰의 embedding row는 1024개의 값으로 이루어져 있습니다. 이를 32개 단위 block으로 나누면 1024 / 32 = 32 blocks가 됩니다.

d_embeddingblock 개수FP16 row 크기Q4_0 row 크기
10241024 / 32 = 321024 × 2 = 2048 bytes32 × 18 = 576 bytes
768768 / 32 = 24768 × 2 = 1536 bytes24 × 18 = 432 bytes

아래 그림은 하나의 Q4_0 block이 scale 1개와 16개의 byte(=32개의 4bit code)로 구성됨을 보여줍니다.

여기서 d=768 사례처럼 24 blocks로 나눠지는 경우처럼, embedding 차원이 32의 배수가 아니면 block 경계 처리 방식은 구현마다 다름 — padding을 두는지, 다른 quant type을 섞는지는 quantize 스크립트와 llama.cpp 버전에 따라 달라질 수 있습니다.

5.Nibble Packing: 4bit를 1byte 안에 두 개씩 담기

nibble은 4bit짜리 조각을 가리키는 이름입니다. 1 byte는 8bit이므로, nibble 두 개를 정확히 담을 수 있습니다. 관례적으로 byte의 하위 4bit을 lower nibble, 상위 4bit을 upper nibble이라고 부릅니다. Q4_0의 qs 배열은 이런 식으로 4bit code 두 개를 byte 하나에 우겨넣어 저장합니다 — 이것이 "GGUF Q4_0 tensor의 tensor data 저장 형식"이 nibble packing이라 불리는 이유입니다.

비트 연산으로 표현하면, 어떤 byte 값에서 lower/upper nibble을 꺼내는 방법은 다음과 같습니다.

byte = 0xC3;               // 1100 0011 (2진수)

lower = byte & 0x0F;        // 하위 4bit만 남김 → 0011 → 십진수 3
upper = byte >> 4;          // 상위 4bit을 오른쪽으로 밀어냄 → 1100 → 십진수 12

// Q4_0는 이 4bit 값(0~15)에 -8을 적용해 대략 -8~7 범위의 signed code처럼 사용
lower_code = lower - 8;     // 3 - 8 = -5
upper_code = upper - 8;     // 12 - 8 = 4

// 최종 weight 근사값 = scale * code

즉 하나의 byte 0xC3는 서로 다른 두 weight의 code를 담고 있는 셈입니다. lower nibble에서 나온 -5와 upper nibble에서 나온 4는 각각 block의 scale과 곱해져 원래 weight의 근사값으로 복원됩니다.

구현 확인 필요 — 여기서 설명한 "byte 하나 = 인접한 weight 두 개"라는 매핑은 개념을 이해하기 위한 단순화입니다. 실제 llama.cpp의 quantize_row_q4_0 / dequantize_row_q4_0 구현에서는 qs[j]의 lower/upper nibble이 weight[j], weight[j+16]처럼 서로 16칸 떨어진 위치에 매핑되는 등, 단순 짝수/홀수 순서(q0, q1, q2...)와는 다른 인덱싱을 쓸 수 있습니다. 이 문서는 nibble packing이라는 개념 자체를 설명하는 것이 목적이며, 정확한 인덱스 순서는 실제 소스 코드로 확인해야 합니다.

6.Activation이란 무엇인가 — activation function이 아니다

이 문서에서 가장 자주 오해가 생기는 단어가 activation입니다. 딥러닝을 처음 배울 때 activation이라는 단어는 ReLU, GELU 같은 activation function을 먼저 떠올리게 만들지만, matmul/kernel 최적화 맥락에서 activation은 그것이 아닙니다.

matmul 관점에서 activation은 "현재 계산에 입력으로 들어가는 tensor", 즉 hidden state입니다. 예를 들어 attention의 Query projection은 q_cur = Wq × normed_hidden처럼 계산되는데, 여기서 Wq는 weight(고정된 학습 파라미터)이고 normed_hidden이 바로 activation입니다. 즉 activation function을 통과한 결과물이라는 좁은 의미가 아니라, "이번 matmul의 입력으로 흘러 들어오는 값"이라는 더 넓은 의미로 쓰입니다.

이 구분이 왜 중요한가 하면, weight와 activation은 성격이 완전히 다르기 때문입니다. weight는 학습이 끝난 뒤 고정된 값이므로, 모델을 배포하기 전에 미리 Q4_0으로 양자화해서 파일에 구워 넣을 수 있습니다. 반면 activation(=hidden state)은 토큰마다, 레이어마다, 입력 문장마다 실시간으로 달라지는 값입니다. 그래서 activation은 GGUF 파일 안에 미리 저장해 둘 수가 없고, 추론이 실행되는 매 순간 그 자리에서 계산되어야 합니다.

따라서 실제 matmul 커널 안에서는 weight 쪽만 Q4_0 형태로 미리 준비되어 있고, activation 쪽은 런타임에 FP16/F32 형태 그대로 쓰이거나, 필요하다면 Q8_0처럼 좀 더 정밀도가 높은 8bit 형태로 즉석에서(on-the-fly) 양자화되어 block/tile 단위로 준비될 수 있습니다. 어느 방식을 쓰는지는 backend 구현마다 다름 — 이는 HTP backend가 activation을 FP16 그대로 넘기는지, Q8로 변환해서 넘기는지에 따라 달라지는 부분입니다.

7.FP16 matmul과 Q4_0 matmul 비교

FP16 matmul

가장 단순한 경우인 FP16 matmul에서는, 32개 weight를 읽으려면 64 bytes를 메모리에서 읽어야 하고, 그 값과 activation을 그대로 FP16 multiply-add로 누산합니다. 구조는 단순하지만, weight 하나하나가 2 bytes를 차지하므로 weight memory traffic이 큽니다. 대규모 언어모델에서는 decode 단계마다 이 weight들을 반복해서 읽어야 하므로, 이 memory traffic이 실제 속도를 좌우하는 병목이 되는 경우가 많습니다.

Naive Q4_0 matmul (비권장 경로)

Q4_0을 도입할 때 가장 이해하기 쉬운 방법은, block 전체를 통째로 FP16/F32로 dequantize해서 임시 weight buffer를 만든 다음, 그 임시 buffer로 기존과 동일한 FP16 matmul을 수행하는 것입니다. 이 방식은 개념적으로는 쉽지만, dequantize에 드는 연산과 임시 buffer용 메모리 대역폭을 추가로 써버리기 때문에 Q4_0이 주는 이점을 상당 부분 잃습니다. 즉 "일단 원래 크기로 풀어서 계산한다"는 접근은 압축의 목적(메모리 절감)을 스스로 무너뜨리는 셈입니다.

Optimized Q4_0 matmul (실제로 이득을 보는 경로)

실제로 속도 이득을 보려면 dequantize를 별도의 큰 단계로 분리하지 않고, block/tile 단위로 다음 과정을 dot product 계산 자체에 녹여 넣습니다.

  1. block 단위로 Q4 weight(scale + qs 18 bytes)를 읽는다
  2. nibble을 unpack해 4bit code들을 꺼낸다
  3. 같은 구간의 activation block을 읽거나(FP16), 미리 Q8로 준비된 activation block을 읽는다
  4. 정수 dot product(integer dot) 또는 mixed-precision dot을 수행한다
  5. 그 결과에 block scale을 곱한다
  6. 여러 block의 결과를 누산(accumulate)한다
핵심 포인트 — "dequantize"라는 이름의 별도 단계가 크게 따로 존재하는 것이 아니라, unpack과 scale 적용이 dot product 루프 안에 녹아 들어가 있는 형태(fused)입니다. 이렇게 하면 weight를 원래 크기로 복원한 임시 버퍼를 메모리에 다시 쓰고 다시 읽는 왕복 비용이 사라집니다.

단, 이 최적화 경로는 backend와 하드웨어 조건이 맞을 때만 실제로 타게 됩니다. 조건이 맞지 않아 fallback 경로(예: naive dequantize 경로나 CPU 범용 경로)로 빠지면, Q4_0을 쓰더라도 기대했던 만큼의 속도 이득은 줄어들 수 있습니다 — 이는 backend/조건에 따라 다름.

8.Scale이 있는데 왜 빨라지는가

여기서 자연스러운 의문이 생깁니다: "FP16은 그냥 곱하고 더하면 끝인데, Q4_0은 scale까지 곱해야 하니 연산이 하나 더 늘어난 것 아닌가? 그런데 왜 더 빠르다고 하는가?" 이 질문에 답하려면 수식을 조금 풀어볼 필요가 있습니다. 

// 원래 하고 싶은 계산 (32개 항의 dot product)
sum_i  activation_i * weight_i

// Q4_0 + activation quantization을 적용하면 이렇게 근사됨
sum_i (a_i_int8 * scale_a) * (q_i_int4 * scale_w)
  = scale_a * scale_w * sum_i( a_i_int8 * q_i_int4 )

FP16 계산에는 이런 scale 곱이 없으니, 딱 이 수식 하나만 놓고 보면 Q4_0 쪽이 더 복잡해 보이는 것이 사실입니다. 하지만 여기서 짚어야 할 것은 "연산 개수"와 "실행 비용"은 다른 개념이라는 점입니다.

32개 항을 곱하고 더하는 dot product의 수학적 항 개수는 FP16이든 Q4_0이든 동일하게 32개입니다. Q4_0이 빨라지는 이유는 이 항의 개수를 줄여서가 아니라, 다음 몇 가지 요인이 겹쳐서입니다.

  • weight memory bandwidth 절감 — 32개 weight를 읽는 데 64 bytes 대신 18 bytes만 읽으면 되므로, 특히 decode처럼 weight를 매번 새로 읽어야 하는 memory-bound 상황에서 이득이 큽니다.
  • cache/VTCM 효율 — 더 작은 데이터가 더 좁은 온칩 캐시나 HTP의 VTCM(scratchpad memory)에 더 많이 들어갈 수 있어, 반복 접근 시 재사용률이 올라갑니다.
  • packed/vector dot 연산 — 4bit로 눌러 담긴 데이터는 벡터 유닛이 한 번에 더 많은 code를 동시에 처리(packed integer dot)할 수 있게 해줍니다.
  • scale 비용의 block 단위 amortization — scale 곱셈은 원소 하나마다가 아니라 block(32개)마다 한 번만 일어납니다. 즉 scale 곱 1회의 비용을 32개 원소가 나눠 짊어지므로(amortize), 원소당 추가 비용은 매우 작습니다.
정리 — Q4_0의 이득은 "곱셈 덧셈 항의 개수를 줄여서"가 아니라, weight를 읽어오는 byte 수와 하드웨어에 데이터를 공급(feeding)하는 비용을 줄여서 생깁니다. 특히 LLM decode처럼 한 번에 토큰 하나씩만 처리하면서 거대한 weight 행렬 전체를 훑어야 하는 상황(=memory-bound)에서는, 연산 자체보다 "weight를 얼마나 빨리 가져올 수 있는가"가 속도를 좌우하기 때문에 이 memory bandwidth 절감 효과가 두드러집니다.

9.Row-major와 Tile-major layout

weight 데이터를 메모리에 어떤 순서로 늘어놓을지는 그 자체로 성능에 큰 영향을 줍니다. 이해를 돕기 위해 실제 block size(32) 대신, 작은 예시로 4 rows × 8 cols 행렬을 block size 2로 나눈 경우를 살펴보겠습니다.

row-major 저장은 우리가 흔히 생각하는 방식입니다: 첫 번째 row의 block들을 순서대로 다 쓴 다음, 두 번째 row의 block들을 순서대로 쓰는 식입니다.

이 개념을 실제 HTP 관점의 크기로 확장하면, 예를 들어 32 rows × 32 K-values 크기의 타일을 기준으로, "rows 0~31의 K0~31"을 먼저 전부 모아서 저장하고, 그다음 "rows 0~31의 K32~63"을 모아서 저장하는 식으로 진행됩니다. 즉 K(입력 차원) 방향으로 32개씩 잘라, 그 구간에 대해 32개 row(출력 채널)를 한꺼번에 훑을 수 있는 순서로 데이터를 미리 정리해 두는 것입니다.

tile-major layout의 의미 — 이것은 새로운 양자화 방식이 아니라, HTP kernel이 실제로 데이터를 읽는 순서에 맞춰 미리 정리해 두는 재배치입니다. kernel이 한 번에 32개 output row에 대해 같은 activation 구간을 재사용하면서 연산하고 싶다면, weight도 그 순서에 맞게 미리 늘어서 있는 편이 캐시/VTCM에서 연속적으로 읽기에 유리합니다. row-major 그대로 두면 이런 재사용 패턴을 만들기 위해 매번 건너뛰며 읽어야 하므로 비효율적입니다.

10.HTP0-REPACK: 재양자화가 아니라 layout 재배치

HTP0-REPACK이라는 이름 때문에 "다시 양자화하는 과정인가?"라고 오해하기 쉽지만 그렇지 않습니다. HTP0-REPACK은 이미 Q4_0으로 양자화되어 있는 weight를, 값은 그대로 둔 채, HTP kernel이 선호하는 tile-major/aligned 레이아웃으로 다시 포장한 buffer입니다. 즉 quantize(정밀도를 낮추는 과정)가 아니라 pack/layout 변환(바이트 순서를 바꾸는 과정)입니다. 

// 개념적인 HTP0-REPACK 과정 (실제 구현의 세부 순서와는 다를 수 있음)
1. GGUF에서 Q4_0 block(scale + qs)을 읽는다
2. scale과 qs를 각각 읽어온다
3. 필요하면 nibble을 unpack한 뒤 원하는 순서로 다시 repack한다
4. 32x32 같은 tile 단위로 데이터를 재배치한다   (row-major → tile-major)
5. scale들의 저장 위치도 tile에 맞춰 재배치한다
6. HTP가 요구하는 byte 정렬(예: 64/128 byte alignment)에 맞춰 padding을 넣는다
7. 결과를 HTP0-REPACK buffer에 저장한다

여기서 확정적으로 말할 수 있는 것은, HTP0-REPACK이 값 자체(scale, code)를 바꾸지 않는다는 점입니다. bit 단위로 표현되는 숫자적인 정보량은 동일하되, 그 바이트들이 메모리 상에서 어떤 순서로 나열되는지만 바뀝니다.

PoC에서 실제로 부딪히는 리스크 — token_embd.weight 같은 input embedding 텐서가 CPU_Mapped buffer에 그대로 남아 있으면, embedding 조회 연산인 GET_ROWS가 HTP 실행 경로를 타지 못할 수 있습니다 가능성. transformer block 내부의 weight(attn_q, attn_k, ffn_up 등)는 HTP0-REPACK 대상이 될 여지가 있지만, input layer(embedding)를 어떻게 다룰지는 backend의 placement 정책에 따라 달라질 수 있습니다 구현마다 다름. 따라서 PoC에서는 "이 텐서가 정말 HTP0-REPACK 버퍼에 배치되었는가"를 load_tensors 단계의 placement 로그로 직접 확인하는 작업이 꼭 필요합니다.

11.Graph Build와 Scheduler

모델이 로드된 뒤, 추론을 실행하기 전에 llama.cpp는 실제 계산을 곧바로 수행하지 않고 먼저 연산 그래프를 만듭니다. 이 단계에서 자주 등장하는 함수들의 역할을 명확히 구분할 필요가 있습니다.

  • create_tensor — 이름 그대로 "텐서를 만든다"고 하면 Q4 bytes를 새로 계산하는 것처럼 들리지만, 실제로는 텐서의 이름·shape·타입을 정의하는 함수에 가깝습니다. 실제 weight bytes는 이미 GGUF tensor data에 있고, 이 함수는 그 데이터를 가리킬 "자리"를 만드는 역할입니다.
  • build_attn, build_ffn, ggml_mul_mat — 이 함수들을 호출한다고 해서 그 순간 행렬곱이 실행되는 것이 아닙니다. 이들은 "이런 계산이 필요하다"는 그래프 노드를 만들 뿐이며, 실제 실행은 나중에 별도로 이루어집니다.
  • ggml_build_forward_expand — 만들어진 노드들과 그 사이의 의존 관계(dependency)를 최종 그래프에 등록하는 역할을 합니다.

그래프가 완성되면 scheduler가 각 노드를 어떤 backend(CPU / HTP / GPU)에서 실행할지 결정합니다. 이때 사용하는 판단 기준이 supports_op(이 backend가 이 연산 종류를 지원하는가)와 supports_buft(이 연산에 연결된 버퍼 타입이 이 backend와 호환되는가)입니다.

중요한 구분 — supports_op가 true라고 해서 그 연산이 반드시 HTP에서 실행된다는 뜻은 아닙니다 가능성. 최종 실행 backend는 그 연산에 연결된 입력/출력 buffer가 실제로 그 backend와 호환되는지(supports_buft), 그리고 scheduler의 전체적인 split 알고리즘(어떤 조합이 전체적으로 더 효율적인지)까지 함께 고려한 결과로 정해집니다. "op는 지원되지만 buffer 위치 때문에 결국 CPU로 떨어지는" 경우도 실무에서 흔히 발생합니다.

12.HTP graph_compute와 HMX/HVX kernel

scheduler가 어떤 노드를 HTP에서 실행하기로 결정하면, HTP graph_compute라는 host-side(즉 NPU가 아니라 CPU 쪽에서 도는) 준비 코드가 그 노드들을 실제 DSP 작업으로 바꿔주는 역할을 합니다. 이 단계가 하는 일은 대략 다음과 같이 정리할 수 있습니다.

  • graph를 캐시해 두고 재사용 가능한 부분을 구분한다 (graph cache)
  • 실행해야 할 compute node들을 추출한다
  • 가능한 연산들을 하나로 묶는다 (fusion)
  • GGML의 범용 연산자를 HTP 고유의 opcode로 매핑한다 (op remap)
  • matmul에 필요한 shape/stride 등의 파라미터를 계산한다
  • VTCM(온칩 scratchpad 메모리) 사용량이 허용 범위인지 확인한다
  • 준비된 작업을 dspqueue에 enqueue해서 실제 DSP 코어로 넘긴다

이렇게 DSP로 넘어간 작업은 실제 Hexagon 코어 내부의 여러 실행 경로 중 하나를 타게 됩니다. 이 경로들은 일반적인 HTP/HVX/HMX kernel 관점에서 다음과 같이 구분해 볼 수 있습니다 — 정확한 내부 스케줄링 로직은 Qualcomm의 비공개 구현 영역이므로, 아래는 공개된 개념과 코드 관찰에 기반한 일반화된 설명입니다.

  • HMX (Hexagon Matrix eXtension) — 행렬곱 자체에 특화된 하드웨어 유닛을 사용하는 path 가능성
  • HVX tiled — 벡터 연산 유닛(HVX)을 쓰되, 타일 단위로 정렬된 레이아웃을 활용하는 path
  • HVX flat — 타일 최적화 없이 좀 더 단순한 벡터 연산으로 처리하는, 상대적으로 fallback 성격의 path
  • CPU fallback — HTP 실행 조건이 맞지 않을 때 결국 CPU 범용 코드로 처리되는 경로

이 경로들이 일반적인 CPU for-loop 기반 matmul과 근본적으로 다른 지점은, 데이터를 한 원소씩이 아니라 타일(tile) 단위로 한꺼번에 공급한다는 점입니다. CPU의 단순 for-loop는 메모리에서 값을 하나씩(또는 SIMD 폭만큼) 읽어와 곧바로 계산하는 반면, HMX/HVX 경로는 미리 정렬된 tile 데이터를 VTCM이라는 온칩 scratchpad에 올려두고, packed data 형태와 벡터 lane을 최대한 활용해 여러 원소를 동시에 처리합니다. 이 방식이 성능을 내려면 데이터가 이미 정해진 alignment와 layout(즉 앞서 설명한 tile-major, HTP0-REPACK)을 전제로 깔고 있어야 하며, 이 전제가 깨지면 최적화된 경로 대신 flat/fallback 경로로 빠지게 됩니다.

13.Decode 1 Step 예시

지금까지의 개념들이 실제 추론 한 스텝(토큰 하나를 생성하는 과정)에서 어떻게 이어지는지 순서대로 따라가 보겠습니다.

이 흐름에서 각 matmul 연산이 실제로 HTP에서 실행되려면, 앞서 설명한 것처럼 단순히 "op가 지원된다"는 것만으로는 부족합니다. 그 연산의 입력(src)과 출력(dst) buffer가 모두 HTP와 호환되는 위치에 있어야 하며, 특히 Q4_0 weight를 쓰는 matmul이라면 그 weight가 HTP0-REPACK 버퍼에 배치되어 있는지, 그리고 실행 시점에 HMX 또는 HVX tiled path를 실제로 타는지가 성능을 가르는 핵심 확인 지점이 됩니다. GET_ROWS처럼 그래프의 맨 앞에 있는 연산 하나가 CPU_Mapped 상태에 머물러 있으면, 그 뒤에 이어지는 연산들의 activation 흐름 전체가 CPU와 HTP 사이를 오가며 불필요한 복사/동기화 비용을 만들 수 있습니다.

14.실무 디버깅 체크포인트

PoC를 진행하면서 "정말 Q4_0 weight가 HTP tiled matmul 경로로 실행되고 있는가"를 확인하려면, 최소한 아래 항목들을 로그나 실행 조건에서 직접 확인하는 과정이 필요합니다.

[확인 체크리스트]
1. token_embd.weight 의 타입 확인            → F16 / F32 / Q4_0 중 무엇인가
2. token_embd.weight 의 buffer placement 확인 → CPU_Mapped 인가, HTP0 계열인가
3. HTP0-REPACK 버퍼로 배치되었는지 여부       → load_tensors 로그에서 확인
4. repack_q4_0_tiled(또는 유사 함수) 호출 여부 → repack 단계가 실제로 실행됐는가
5. supports_get_rows 의 반환 사유(reason)     → 왜 HTP/CPU로 갈렸는지
6. supports_mul_mat 의 반환 사유(reason)      → 왜 HTP/CPU로 갈렸는지
7. supports_buft 통과 여부                    → buffer 타입 호환성 확인
8. OPTRACE 상 CPU/HTP 노드 split 비율         → 그래프 전체에서 HTP 비중
9. graph_compute 단계의 fusion/remap 적용 여부 → 연산이 실제로 결합/변환됐는가
10. HMX / HVX tiled / HVX flat 중 어느 경로인지 → 실행 path 식별
11. VTCM 부족으로 인한 fallback 발생 여부      → 용량 초과 시 flat/CPU로 밀림
가장 흔한 착각 — "이 모델은 Q4_0으로 양자화되어 있다"는 사실과 "이 matmul이 실제로 Q4_0 HTP tiled path에서 실행되고 있다"는 사실은 전혀 다른 주장입니다. 전자는 GGUF 파일의 정적인 속성이고, 후자는 런타임에 buffer placement와 scheduler 판단과 커널 선택이 모두 맞아떨어져야 성립하는 동적인 사실입니다. PoC의 성공 여부를 판단할 때는 반드시 후자를 로그로 직접 확인해야 합니다.

15.마무리

Semantic Agent PoC처럼 온디바이스 NPU에서 LLM을 실제로 구동하는 프로젝트에서는, "모델이 일단 로드되고 출력이 나온다"는 것만으로는 충분하지 않습니다. 출력이 나오더라도 대부분의 연산이 CPU fallback으로 처리되고 있다면, 그것은 기술적으로는 "동작"하는 것이지만 이 PoC가 증명하고자 하는 "NPU 가속"이라는 목표는 달성하지 못한 것입니다. 그래서 데모의 성공 여부를 판단하는 진짜 기준은 "모델이 실행되었는가"가 아니라 "어떤 연산이 실제로 HTP에서 돌았는가"여야 합니다.

이 문서에서 다룬 내용을 한 문장씩으로 요약하면 다음과 같습니다.

  • GGUF Q4_0은 FP16 weight를 block 단위(32개 + scale 1개)로 압축해 weight 파일 크기와 memory bandwidth 요구량을 줄입니다.
  • HTP0-REPACK은 그렇게 작아진 weight의 값을 바꾸지 않은 채, HTP kernel이 가장 잘 소화할 수 있는 tile-major 순서로 다시 정리합니다.
  • scheduler는 연산 그래프의 노드 하나하나를 살펴 실제로 어떤 backend(CPU/HTP/GPU)에서 실행할지를 나눕니다.
  • HMX/HVX kernel은 tile 정렬, layout 전제, VTCM 활용이라는 조건이 모두 충족될 때 비로소 실질적인 성능 이득을 만들어냅니다.

이 네 가지는 서로 독립적인 조건이며, 어느 하나만 만족한다고 해서 전체가 저절로 따라오지 않습니다. PoC를 검증할 때는 이 네 단계를 각각 별도로 확인하는 습관이, 막연히 "빨라졌다/느리다"는 인상보다 훨씬 신뢰할 수 있는 근거가 됩니다.

16.관련 코드 탐색 키워드
